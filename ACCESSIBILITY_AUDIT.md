# IMC ER — Accessibility & UI Audit

Scope: skeleton loading states, the semantic color system, UI density/clutter, and a WCAG 2.1 AA accessibility pass, covering `public/index.html`, `public/css/design-system-2026.css`, `public/css/style.css`, and `public/js/app.js`. Method was a full manual read of every template and stylesheet, computed WCAG contrast ratios for every foreground/background token pair actually used as text, and interaction testing of the modal dialogs and focus behavior in a headless browser against the static markup (the app's real views sit behind Firebase auth, which this environment has no credentials for, so live authenticated screens — the actual populated patient board, the Owner tab with real accounts — were not walked end-to-end; the recommendation at the end covers how to close that gap).

## What was already in good shape

This codebase came in far more mature than a typical first pass. Skeleton loaders are already comprehensive: the full-page loading overlay, the patient list, the discharged list, and the Owner tab's user list all ship with pre-baked skeleton markup in `index.html` rather than a blank flash while Firebase resolves, and the overlay stays up until the first real data snapshot has already rendered underneath it, so there's no visible gap between skeleton and content. The semantic color system in `design-system-2026.css` is similarly thorough and genuinely tied to what the app does: a dedicated escalation ramp for length-of-stay, distinct role-identity colors for the account hierarchy, and a red/amber/green triage vocabulary that's driven by data attributes rather than duplicated per component. Touch targets are enforced at 48px globally, `:focus-visible` outlines are already applied everywhere interactive, and typography uses fluid `clamp()` scaling rather than fixed breakpoints. None of that needed rework, and the fixes below build on it rather than replacing it.

## Contrast failures found and fixed

Every token pair actually used as text was run through the WCAG relative-luminance formula (not just eyeballed), which surfaced four real AA failures, all now fixed in `design-system-2026.css` and `style.css`:

The dark-theme length-of-stay ramp had a hard bug: text contrast on the six LOS metric cards degrades steadily from 8.2:1 at the ">4 Hrs" tier down to 2.63:1 at ">72 Hrs" — the exact opposite of what you'd want, since >72 Hrs is the tier that most needs to read clearly at a glance. The fix adds a second on-color token, `--on-los-hi`, used only on the >48h and >72h tiles, so those two switch to light text (4.81:1 and 6.65:1) while the lighter tiers keep dark text.

The dark-theme "Register Patient" hero button — the single most-used action in the app — had cream text on brand-orange at 2.96:1, under even the large-text minimum. `--on-cta` for dark theme now uses the same dark-text-on-mid-tone trick the codebase already used for `--on-primary`, landing at 5.9:1.

The light-theme CTA had the mirror problem from the other direction: white text on the light-theme orange was only 4.36:1, borderline-failing at the button's actual text size. The light-theme `--cta` was darkened slightly (`#b8613f` → `#ab5636`) to bring white text to 5.1:1 without changing the color's identity.

The Owner tab's role badges (`.user-card-role`, 13px bold — too small to qualify for the relaxed large-text threshold) failed for three of seven roles in light theme: Owner at 3.5:1, Emergency Manager at 3.6:1, Deputy Manager at 4.3:1. Those three role tokens were darkened by one step each (verified back above 4.5:1 against the actual card background) while keeping every dark-theme value and the four roles that already passed untouched.

## Modal dialogs made keyboard- and screen-reader-accessible

The four modals (patient registration, room picker, department picker, discharge) were purely visual: `.hidden` toggled on and off with no `role="dialog"`, no focus ever moving into the dialog, no keyboard trap, and no Escape-to-close. A keyboard user opening "Register Patient" could `Tab` straight through the form and out into the dashboard behind it. This is now a single pair of helpers (`openModalDialog` / `closeModalDialog` in `app.js`) wired into every open/close call site, including the generic backdrop-click and "×" handlers, so the fix applies uniformly rather than per-modal. Opening a dialog now moves focus to its first real field (skipping the close button, so a screen-reader/keyboard user doesn't land on "dismiss" first), `Tab`/`Shift+Tab` are trapped inside the dialog's own focusable elements, `Escape` closes it, and closing — by any path — returns focus to whatever originally opened it. All four dialogs now carry `role="dialog"`, `aria-modal="true"`, and `aria-labelledby` pointing at their own heading. This was verified with a headless-browser interaction test, not just read through: opening the registration modal lands focus on the name field, tabbing past the last field wraps back to the close control, and Escape returns focus to the "Register Patient" button that opened it.

## Other WCAG gaps closed

Switching the UI to Arabic updated the page's `dir` attribute for layout but never updated `lang`, so a screen reader kept reading the Arabic text with English pronunciation rules after the switch (WCAG 3.1.1). `updateTranslations()` now sets `document.documentElement.lang` alongside `dir`. The critical-vitals sentinel banner had no way to reach a screen-reader user who wasn't looking at the screen when a patient's vitals turned critical; it now carries `role="alert"` and `aria-live="assertive"`. The dynamically-created "failed to load patients" banner gets the same `role="alert"`, and its click-to-dismiss affordance — previously a `<div>` with only a mouse handler — is now independently keyboard-focusable and operable. Typing in the patient search box now announces the match count through a visually-hidden live region, scoped to the search input's own event so it doesn't fire on every real-time Firestore update elsewhere on the page (which would have buried the one announcement that actually matters under constant chatter).

## Decluttering

The Shift Analytics panel hand-rolled the same `style="background: var(--card-bg); border: 1px solid var(--border-color); padding: 14px; border-radius: 12px; text-align: center;"` block inline five separate times for its stat tiles, plus four more inline blocks for the admissions breakdown — diverging slightly each time, including one copy that referenced `--bg-main`, a token that was never defined anywhere in the codebase and was silently rendering as transparent. That's now two small reusable classes (`.stat-tile` and `.admissions-breakdown`), which also fixed the transparent-background bug and made the admissions breakdown grid responsive instead of a fixed four columns that didn't fit a phone screen. Separately, the skeleton-loader shimmer effect had accumulated three near-identical `@keyframes` (`skeletonPulse`, `skeleton-pulse`, `skeletonShimmer`) split across both stylesheets, where only the last-loaded one ever actually rendered — the other two were pure dead weight. These are now consolidated to the one that was actually winning. While tracing that, four of the patient-card skeleton placeholders turned out to reference an inline `animation: pulse ...` pointing at a keyframe named `pulse` that was never defined anywhere in either file — those four skeletons were rendering as a static gradient with no shimmer at all. That's fixed as part of the same consolidation.

## What wasn't done, and why

A few things came up during the review that are worth flagging rather than fixing unilaterally. `text-muted` (secondary) text sits at roughly 4.3:1 against card backgrounds in light theme — under the 4.5:1 line, but only marginally, and it's used in dozens of places (timestamps, field labels, meta text) where darkening it enough to pass would be a visible, app-wide tone shift. That's a judgment call for whoever owns the visual design, not something to change quietly as part of a contrast pass. The app also has no skip-to-content link and no explicit `<main>`/landmark structure, which would help screen-reader users jump past the header and tab bar — reasonable to add, but it touches the top-level page structure rather than being a contained fix. Finally, and most importantly: this review covers the code as written, not the authenticated app running against live data — the room/department picker interactions, the real patient board at scale, and RTL Arabic rendering with actual Arabic content were reviewed statically, not click-tested end to end, because that requires signing in. If a live pass would help, the browser tools available in this session can drive your own logged-in browser directly against the deployed app; that's a natural next step if useful.
